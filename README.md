# xlang

一步一步实现一个解释器：词法分析 → Pratt 解析 → AST → 字节码 → 栈式虚拟机。

## 目录结构

| 包 | 职责 |
| --- | --- |
| `lexer` | 词法分析。`Char` 是值类型，`unicode` 分类，最长匹配运算符表，支持 `\xNN`/`\uNNNN` 转义与 `0x`/`0o`/`0b`/`_` 数字字面量 |
| `parser` | Pratt 解析器。统一的游标契约（`cur` 恒为下一个待消费 token）、`token(k)` 前瞻、`endStatement()` 收束语句、`synchronize()` 错误恢复，报错带 line/col |
| `ast` | 语法树。每个节点都能给出源码行号（`Line()`），供运行时错误定位 |
| `parser/symtable.go` | 符号表。函数级共享的局部槽位计数、块作用域、`FindScope` |
| `compiler` | AST → 栈式字节码。块作用域、循环上下文、复合赋值、行号表 |
| `bytecode` / `code` | 字节码容器、操作码定义与反汇编 |
| `vm` | 栈式虚拟机。栈与帧按需增长，运行时错误统一带函数名与行号 |
| `cfg` | 基本块划分、可达性、`Compact`（删死块/冗余跳转）、支配树与支配边界 |
| `ir` | 三地址码 IR、SSA 构造、优化、降级回字节码 |
| `cmd/xlang` | 命令行：执行 `.xl` / `.xlc`，可生成缓存（见"命令行与 .xlc 缓存"） |
| `bytecode/xlc.go` | `.xlc` 的编解码与结构校验（magic + 版本 + 源文件指纹 + 逐字段边界检查） |
| `bench` | 算法语料与跨语言对比：`algorithms/<name>.xl` 与 `<name>.py` 一一配对，`compare.py` 跑分 |

## 编译管线

```
源码 ──lexer──► tokens ──parser──► AST ──compiler──► 栈字节码 ──ir──► 优化后的字节码 ──vm──► 结果
```

`ir` 是可选的一层，默认开启。它把"栈位置"变成"有名字的值"：

```
栈字节码 ──stack-to-register promotion──► 三地址码
        ──CFG + 支配树──► SSA（Cytron 算法插 phi）
        ──常量折叠 / 分支化简 / CSE / DCE / 不可达块删除──►
        ──寄存器分配（活跃分析 + 冲突图着色）──► 降级回栈字节码
```

**契约**：优化器对**每个函数**独立地"要么等价改写，要么原样保留"。
因此返回的字节码总是行为等价的，调用方可以无条件采用；error 只带出第一个
放弃原因（诊断用）。

当前会放弃优化的情形：

- REPL 的隐式打印 —— IR 尚未建模；
- 基本块边界上操作数栈非空 —— 需要"栈上的 phi"，收益低且容易出错；
- 任何自检失败（例如读到未定义的槽位）；
- 创建或访问捕获变量的闭包（捕获槽位暂不参与 SSA，按函数保留原字节码）。

方法调用（如 `a.append(x)`）已纳入 IR：方法返回值与更新后的接收者作为两个
SSA 值建模，并作为堆副作用屏障，避免 CSE 或延迟下标读取越过容器修改。
放弃优化仍按函数隔离：某个函数自检失败不会影响其他函数。

关闭优化：

```go
c := compiler.NewCompiler()
c.SetOptimize(false)
```

实测（`ir` 包的等价性语料，25 个程序合计）：**819 → 551 字节（-32%）**。

已知的取舍：赋值表达式（`g = f()` 这种把赋值当值用的写法）在原始字节码里
直接把值留在操作数栈上，而 IR 必须"存槽位 + 读回"，每个这样的点会多 3 字节；
循环变量的 phi 拷贝同理（等实现 phi 拷贝合并后消失）。

## 命令行与 .xlc 缓存

```
xlang [flags] program.xl      # 编译并执行（旁边有可用的 .xlc 就直接用）
xlang [flags] program.xlc     # 直接执行缓存文件

  -write-cache   编译成功后把 .xlc 写到源文件旁边
  -no-cache      既不读也不写 .xlc（总是从源码编译）
  -opt           是否启用 IR/SSA 优化（默认 true）
  -v             打印缓存命中 / 失效原因
  -q             不打印最后一条语句的值
```

退出码：`0` 成功、`1` 编译或运行时错误、`2` 用法错误。

缓存策略照抄 `.pyc` 的思路，但把"不可信输入"当成第一要务：

| 机制 | 做法 | 为什么 |
| --- | --- | --- |
| 识别 | 文件头 `XLC1` + 格式版本 `u16` | 解释器升级（操作码/结构/语义变化）后旧缓存自动作废，不会读到"看起来能跑"的错字节码 |
| 新鲜度 | 源文件 `size + mtime` 先比，不一致再比 **SHA-256** | 快路径零成本；`touch` 过但内容没变仍可命中，内容变了而 mtime 没变也能发现 |
| 一致性 | 记录生成缓存时的 `-opt` 开关 | 优化开/关的字节码不同，混用会让"缓存命中"变成随机行为 |
| 载入校验 | 逐字段边界检查 + 常量/方法名下标检查 + `code.MaxStack` 数据流校验 | 损坏、截断、伪造的文件都当成"没有缓存"重新编译 |
| 写入 | 先写临时文件再 `rename` | 中途失败不会留下半个缓存；写不进去（只读目录）只提示，不影响运行 |
| 只存必需的符号信息 | 方法名表（`OpCallMethod` 的操作数要用它查实现） | 省掉整个符号表的序列化；局部变量名只影响反汇编美观度 |

实测（200 个函数的合成程序）：从源码编译 + 优化 **36.9 ms**，直接载入缓存
**19.6 ms**（其中约 19.8 ms 是进程启动地板），缓存文件 28 KB。
所以缓存在"启动一次跑一个脚本"的场景里省的是**编译+优化**那一段；
脚本越大收益越明显。

## 性能

`vm` 包有基准测试（`go test -run XXX -bench . ./vm/`）。解释器循环里有几处结构性开销，
已经按"先测再改"的顺序处理：

| 项 | 做法 | 依据 |
| --- | --- | --- |
| 当前帧 | 把 `frame`/`ins`/`ip` 提到局部变量，只在 push/pop 帧后重新装载 | `currentFrame()` 原本每条指令要调用 3~6 次，每次都做"取下标+边界检查+乘 sizeof(Frame)"；CPython 3.11 的"帧留在局部变量里"是同一思路 |
| 帧的局部槽位 | 所有帧共享一块按栈方式分配/回收的槽位区（`vm.locals`），返回时只回退 `localsTop` | 原来每次调用都要 `make([]object.Object, n)`；CPython 3.11 的连续 frame chunk 同理 |
| 小整数/布尔 | `-256..2048` 的整数与 `true`/`false` 常驻单例 | 每次算术结果装箱都是一次堆分配 |
| 算术分派 | 用类型断言代替 `Type()` 字符串比较 | `Type()` 返回的是字符串，一次算术要比较好几轮字符串 |
| 数组字面量 | `make` + `copy` 取代 append 循环 | 避免多次扩容 |
| 调用路径 | 帧在帧栈里原地构造（`pushFrame` 返回指针），`CompiledFunc` 传指针 | `CompiledFunc` 约 104 字节、`Frame` 约 120 字节，原来每次调用要拷 6 次 |
| 栈操作 | 编译期算出每函数的操作数栈上界，建帧时一次性预留；循环里不再检查容量 | 见下节 |
| **超指令融合** | 把 `GetLocal/GetGlobal/Constant + … + 二元运算` 等固定搭配合并成一条指令 | 减少派发次数（详见下节） |
| **方法调用单指令化** | `OpCallMethod` 直接带"方法名下标 + 实参个数"，实现按接收者类型查表 | 原来 `OpLoadMethod` + `OpCallMethod` 两条指令：一次多派发、一次字符串 map 查找、一次方法对象装箱，方法本身还要 `[]Object{self,val}` 额外分配 |
| **phi 拷贝合并** | 边上的拷贝改成并行拷贝（先全部求值、再全部写回），并按干涉图做 coalescing | 循环携带变量不再每轮"存一次再取一次" |

### 方法调用：从三个分配降到一条指令

`a.append(x)` 原来编译成 `OpLoadMethod` + `OpCallMethod`，运行时要：
`top().Type()`（`ObjType` 是 string，比较是 memcmp）→ `FindMethod` 字符串
map 查找 → 把方法对象装箱进 `object.Object` → 调用后再拼一个
`[]Object{self, val}` 返回。1.6M 次 append 实测 **176 ns/次**（CPython 48 ns）。

现在：

- 编译器只发一条 `OpCallMethod [方法名下标 u16][实参个数 u8]`，方法名在符号表里；
- VM 在 `Run` 开始时按本次字节码构建 `MethodTables`（按对象类别分行），
  调用时用**类型断言**（不是 `Type()` 字符串比较）选出类别，再取下标；
- 方法实现签名改成 `func(self Object, args []Object) (Object, Object, error)`：
  返回"新 self + 返回值 + 错误"，**不再分配** `[]Object`。

同一个 1.6M 次 append 的循环：**176 → 120 ns/次（-32%）**。
剩余开销主要来自 `Array` 是值类型、写回时必须装箱（每次一次堆分配），
以及大切片增长时的写屏障与 GC 扫描——这两项要等 NaN-boxing。

顺带修掉一个语义漏洞：旧签名里方法出错只能把 `Error` 塞进返回值数组，
`VM` 会把它当成"新的 self"写回变量——`s.split(1)` 于是**静默成功**并把
`s` 换成 Error 对象。现在错误会正常冒泡成运行时错误。

### 操作数栈：把容量检查挪到编译期

最直白的写法是"每执行一条指令就检查一次剩余栈空间"。那是一次多余的内存读 +
比较 + 分支，实测占解释器开销 5% 左右。三家工业实现都不这么做：

- **CPython**：编译期用 `stackdepth()` 做一遍数据流，把结果写进 code object 的
  `co_stacksize`；帧一次性按 `frame_size = locals + stacksize` 分配，
  求值循环里**没有任何容量检查**。
- **JVM**：`Code` 属性里直接带 `max_stack`，由 javac/校验阶段算出。
- **Lua**：不静态计算，但规定栈上永远至少留 `LUA_MINSTACK`（20）个空位，
  只在"可能一次要很多槽"的指令和函数调用边界调 `luaD_checkstack`。

本项目采用 CPython 的方案，并吸收 Lua 的余量思想：

1. `code.MaxStack`（[code/stack.go](code/stack.go)）对指令流做数据流分析，
   算出操作数栈的精确上界。每条指令的栈效应表必须与 VM 实现严格对应；
   遇到无法静态确定的形态（未知操作码、控制流汇合处深度不一致、栈下溢）
   直接返回错误。
2. 结果存进 `CompiledFunc.MaxStack` / `Bytecode.MainMaxStack`
   （超指令融合会改变指令流，所以融合之后要重算）。
3. VM 在建帧时 `reserveStack(basePoint + 参数个数 + MaxStack + 8)`，
   之后循环里不再逐条检查。那 8 个空位是防御性余量，对应 Lua 的 `LUA_MINSTACK`。
4. 算不出来时用 `code.ConservativeMaxStack` 兜底：每条指令净压栈最多 1 个，
   所以"指令总数"永远是不小于真实峰值的上界——宁可多预留，也不会不够。
5. **安全网**：万一上界算错，Go 的边界检查会把越界变成 panic 而不是内存破坏；
   `Run` 的 defer 里 `recover` 把它转成 `internal: operand stack overflow` 错误，
   不会让进程崩掉。

这套做法的正确性由三类测试守着：

- `code/stack_test.go`：直线代码、分支、循环回边、汇合深度冲突、栈下溢、
  非法跳转目标、未知操作码、融合指令的栈效应、保守兜底；
- `vm/maxstack_test.go`：静态上界与真实峰值逐程序比对（无调用的程序严格相等）、
  深表达式、循环多轮不增长，以及"故意把上界报小"时必须返回错误而不是崩溃；
- `ir/fuse_test.go::TestStaticStackBoundCoversCorpus`：全部语料跑一遍，
  不允许出现任何 `internal: operand stack overflow`。

### 超指令（superinstruction）

解释器每条指令都要付一次派发成本（读 opcode、跳转表间接跳转、读操作数、
调整栈指针）。`a < 10` 在栈式字节码里是三条指令、三次派发，而它只做一次比较。

`code.Fuse` 在 IR 降级之后做一遍模式融合（[code/fuse.go](code/fuse.go)），
把下面三类固定搭配合并成一条：

| 原序列 | 融合后 | 长度 | 派发 |
| --- | --- | --- | --- |
| 两个操作数（局部/常量/全局）+ 比较 + 条件跳转 | `OpCmpBranch` | 10 → 9 字节 | 4 → **1** |
| `OpGetLocal/OpGetGlobal/OpConstant` + 同左 + 算术/比较 | `OpBinFused` | 7 → 7 字节 | 3 → **1** |
| `OpGetLocal/OpGetGlobal/OpConstant` + `OpReturnVal` | `OpReturnOperand` | 4 → 4 字节 | 2 → **1** |
| 算术/比较 + `OpReturnVal` | `OpBinReturn` | 2 → 2 字节 | 2 → **1** |
| `OpClosure k … OpCallFunc n`（callee 是常量函数且只用于这次调用） | `OpCallFuncConst` | 4 → 4 字节 | 少 **1** 条 |

`OpCmpBranch` 把布尔结果完全消掉——不需要写操作数栈、读回来、再转成 bool。
`OpCallFuncConst` 由 IR 降级阶段发射：callee 直接从常量池取，不占操作数栈，
所以每次调用少一条 `OpClosure`。

`OpBinFused` 用 `[kindAB][binOp][idxA][idxB]` 编码，`kindA`/`kindB` 表示操作数
来自局部变量 / 常量 / 全局变量，所以 3×3 种组合只需要一条指令，
不会让跳转表的目标数膨胀（那会伤害分支预测）。

安全约束（缺一不可，全部有 UT 覆盖）：

1. 被合并的序列里，**除第一条外不能是跳转目标** —— 否则跳到中间会错位；
2. 被合并的指令必须来自**同一源码行** —— 否则运行时错误报的行号会变；
3. 所有跳转目标都要**重新映射**到新偏移，行号表同理；
4. 只减少派发，不改变求值顺序、错误信息与行号：融合指令内部调用的是
   与 `OpBin` 完全相同的那份语义实现。

任何可疑情况（未知操作码、跳转目标越界、无法映射）都放弃该处融合；
`Fuse` 出错时原样返回入参，调用方保留未融合的指令流即可，正确性不受影响。
`ir.FusionEnabled = false` 可以关掉整个融合（基准对比与排障用）。

实测（fib(30)，同一台机器）：

```
融合开   135 ms
融合关   170 ms      → 融合本身 -21%
```

fib 函数从 12 条指令降到 **7** 条：

```
 0 OpCmpBranch      n OpLTEq Int(2) → false 13
 9 OpReturnOperand  return n
13 OpBinFused       n OpSub Int(1)
20 OpCallFuncConst  Get Func <fib>, 1
24 OpBinFused       n OpSub Int(2)
31 OpCallFuncConst  Get Func <fib>, 3
35 OpBinReturn      return OpAdd
```

### CFG 维护契约

任何**修改 terminator** 的优化都必须调用 `Function.relink()`
（[ir/graph.go](ir/graph.go)）：它重算 CFG 的边，并按"前驱块指针"把 phi 的实参
搬到新的前驱顺序上，消失的前驱对应的实参被丢弃。

这条契约不是洁癖：`simplifyBranches` 曾经把 `OpBranch` 改成 `OpJump` 却不重连，
于是死块对后续 pass 不可见（IR 层死块删除形同失效），而且一旦有人补上重连，
join 块的 phi 实参就会与前驱错位——实测会让 `if(0)` 的分支返回**错误结果**。

现在每个 pass 结束后 `optimize()` 还会跑 `validate()`：检查 phi 实参与前驱个数、
终止指令位置、跳转目标、以及"被使用的值必须有定义点"。任何一条不成立就返回错误，
调用方按既有契约放弃优化（保留未优化字节码），绝不会把坏 IR 交给 VM。

（顺带修了一个旧问题：`cfg.Compact` 改变指令偏移后没有重映射行号表，
会导致优化后的程序报错行号漂移。现在由 `CompactLines` 一并处理，并有 UT 防护。）

实测（1000 次迭代的整数循环 / fib(18) / 数组下标 / 深递归 300 层）：

```
                    第一轮后        第二轮后        融合后
LoopArith           123771 ns/op    99680 ns/op    76600 ns/op
FibRecursive        911324 ns/op   539000 ns/op   427000 ns/op
ArrayIndex           25980 ns/op    27960 ns/op    16000 ns/op
DeepRecursion        30137 ns/op    26740 ns/op    19800 ns/op

allocs/op: 3589→1912 / 8377→5 / 151→6 / 207→7
```

注：`OpCmpBranch` 在**分支不可预测**的代码上是净收益（fib(24) 实测 -4%），
在"分支高度可预测、且循环体本身在大量分配"的循环上会略慢几个百分点
（推测与间接跳转的目标地址别名有关，属于 CPU 层面效应）。两者相抵仍然划算，
而且它是后续"分支反转 / 跳转穿线"的前置条件。

### fib(30) 横向对比

同一份朴素递归 `fib(n)=fib(n-1)+fib(n-2)`，同一台机器（Ryzen 7 5800X / Windows）：

| 实现 | 端到端（含启动，最好） | 进程内纯计算 | 每次调用 |
| --- | --- | --- | --- |
| xlang（本项目，字节码解释器） | 0.157 s | ~133 ms | ~49 ns |
| CPython 3.14.2 | 0.120 s | ~101 ms | ~38 ns |
| Node 24.21（V8 JIT） | 0.084 s | ~6.7 ms | ~2.5 ns |
| Rust 1.99 `-O`（原生） | 0.009 s | ~1.6 ms | ~0.6 ns |

注：fib(30) 约有 269 万次调用，两种解释器的耗时几乎全在"建帧 + 派发 + 返回"上。
CPython 3.11+ 有专用化指令（`BINARY_OP_ADD_INT`、`LOAD_FAST_BORROW`）和 opcache，
这就是它比本项目快约 1.3 倍的原因；Node/Rust 快的这 20~100 倍来自 JIT/原生编译，不是同一个量级。
关掉超指令融合后 xlang 是 ~180 ms（融合本身 -26%），这就是当前 7 条指令形态的全部余量。
启动开销：xlang 19 ms、CPython 24 ms、Node 78 ms、Rust 8 ms。

### 经典算法横向对比（CPython 3.14.2）

`bench/algorithms/` 下每道题都有配对的 `<name>.xl` / `<name>.py`：算法步骤、数据规模、
输出完全一致（数据由固定 LCG 生成，不依赖语言内置的排序/随机），所以耗时可以直接对比。
算法端到端数据用 `bench/compare.py --runs 9` 运行：每个程序取 9 次中最好的墙钟时间（含启动），
输出结果与 CPython 逐字比对，不一致则直接报错。运行方式：


解读：

- 对象微基准曾显示局部改善：比较从格式化字符串改为按值比较，消除了临时字符串和分配；
  哈希避免了经 `Inspect()` 格式化再解析；数组格式化也少了一次分配。
- **但整体算法集回退约 3.4%**：多数程序主要花在整数运算、数组读写和解释器执行，
  不会频繁触发对象哈希或字符串化；微基准收益不能直接外推成解释器整体提速，因此实验改动已撤销。
- **调用密集的 fib 只慢约 1.3 倍**：这正是前面那些建帧/超指令优化针对的场景；
  CPython 的优势来自专用化指令，而不是架构差异。
- **二维 DP（LCS / 背包）慢约 2.3 倍**：每个格子要做 3~4 次数组读写，
  每次读写都是一次 `object.Object` 接口装箱/拆箱，而 CPython 的 list 元素是
  缓存好的小整数指针。另外 xlang **没有 `[0]*n` 这类批量分配原语**，
  建表只能跑 `.append()` 循环。要吃掉这块差距，优先考虑减少
  `object.Object` 接口装箱和容器分配，而不是继续抠指令派发。
- **矩阵乘法反超 CPython（0.72x）**：内层是纯整数乘加 + 连续下标，
  xlang 的数组是 `[]object.Object` 的切片，索引本身没有 Python 的
  `PyObject` 类型分派开销，所以能把 CPython 的专用化加法优势抵消掉。
- **BFS 网格也反超（0.93x）**：主要是两个 `int` 数组的读写和 `and` 短路判断，
  队列是 `append` + 游标，没有额外的对象分配。
- **堆排序慢约 1.5 倍、二分查找慢约 1.2 倍**：二者都是纯整数、无字符串，
  瓶颈仍是数组读写的装箱开销和循环里的整数运算派发。
- **Two Sum 慢约 1.35 倍**：哈希表访问是该解释器的热点之一，但实验实现未能证明整个基准集有收益。

- 所有程序在优化开/关上结果逐字一致（`TestAlgorithmCorpus` 两条路径都跑）。

> 优化器开/关的**进程内**对比（同一份字节码，排除启动与噪声）：
> fib -19%、n-queens -13%、mergesort -13%、quicksort -3~-13%、two_sum -5%；
> 这组数据测于方法调用尚未纳入 IR 的版本；含 `.append` 的热路径当时会放弃优化。
> 方法调用现已支持，性能数据需要重新跑分后再更新。这轮原始改进主要来自 phi
> 拷贝合并（coalescing），没有它时 n-queens 反而会慢 19%。

## 还没做的优化

按收益排序：**tagged value / NaN-boxing**（彻底去掉 `object.Object` 接口装箱，
这是继续逼近 CPython 的关键一步；实测浮点每次运算都会堆分配）。
直接线索化派发在 Go 里不可行（没有 computed goto，而密集 switch 本来就会编译成跳转表），
函数指针表实测比现在的 switch 慢 23%，不要做。

方法调用通过双结果 `OpMethodCall` 纳入 IR。降级时会在调用点物化两个结果，
并将更新后的接收者写回槽位；方法调用也会阻断可能跨越堆修改的 CSE 和延迟下标读取。

## 语义要点

- 嵌套函数支持捕获外层局部变量和参数，按共享变量而非值快照捕获；外层返回后，
  闭包仍可读写这些变量。同一次调用创建的闭包共享捕获单元，不同调用相互独立。
  多层嵌套会逐层转发捕获单元，局部函数支持递归，也可作为返回值、实参或容器元素。
  局部函数在执行 `def` 时初始化，彼此捕获后可相互递归，但调用前必须完成初始化。
  变量仍使用函数级槽位：同一循环内反复执行声明不会创建每次迭代独立的捕获变量。
- 闭包环境由 Go GC 管理；`.xlc` 保存捕获描述而非运行时环境，载入后重新创建闭包。
  缓存格式版本已升至 3，旧缓存失效后需重新编译。
- `OpDiv` 对整数也返回浮点；`OpMod` 对整数返回整数；`OpPow` 总返回浮点。
- `//`（及 `//=`）是向下取整的除法，与 Python 一致：整数 `//` 整数得整数（`-7//2 == -4`），
  含浮点时结果为浮点（`7.0//2 == 3.0`）；除零报 `division by zero`。
- 整数溢出按 Go 的 `int` 回绕（64 位平台即 int64），不做大整数。
  `MinInt64` 没有对应字面量，需要写成 `(-9223372036854775807-1)`。
- 数值比较是**精确**的：int/int 按整数比较，int/float 拆成整数部分与小数部分比较，
  不经过 float64（否则 2^53 以上相邻整数会被判成相等）。NaN 遵循 IEEE：与任何值都不相等、不有序。
- `not` / `if` / `and` / `or` 共用同一套真值判定（`objToNativeBool`）：
  `0`、`0.0`、`""`、`none` 为假，非零数值与非空字符串为真，数组/Map **恒为真**（不看长度）。
- 浮点显示是 64 位最短往返格式（`1/3` → `0.3333333333333333`）；
  除零与浮点取模除零都报 `division by zero`，不会静默返回 `Inf` / `NaN`。
- 方法（`append`/`pop`/`split`…）出错是**运行时错误**，不会被吞掉：
  `s.split(1)` 报 `TypeError: must be str or None, not Int`，而不会把 `s` 换成错误对象。
- 已知与 Python 不同的两处优先级：`**` 左结合（`2**3**2 == 64`），
  一元负号比 `**` 更紧（`-2**2 == 4`）。若要改成 Python 语义，
  `arith_test.go::TestOperatorPrecedence` 里对应断言要同步修改。
- `if` / `for` 虽然可解析为表达式，但**没有值**（分支里的语句级表达式会被 `OpPop`），
  所以 `var x = if(...){...}` 得到的是 `None`；用 `lastPop`（REPL/脚本末尾）取结果。
- `OpUpdate` 原地修改容器并把容器压回栈；`OpUpdateLocal`/`OpUpdateGlobal` 写槽位但不弹栈。
- `OpPop` 会记录 `lastPop`（REPL 靠它显示结果），因此 IR 里它是 `OpSink`，不是死代码。
- 运行时报错（除零、类型不匹配、下标越界）是程序可观察的行为，优化器不会删除可能报错的指令。
- 脚本最后一条语句是 `if` 时，两个分支都以 `OpExit` 结束；IR 降级会给非末尾块补一条
  跳到脚本末尾的合成跳转，否则 then 分支会顺序落进 else 的代码（回归测试见
  `control_flow_test.go`）。

优化器这两年修过的**错误代码**（都属于"结果错了但没人报错"，全部有回归用例）：

| 症状 | 根因 |
| --- | --- |
| `s += i` 循环多算一轮（10 → 15） | phi 拷贝逐条"读-写、读-写"，后一个实参读到被覆盖的值 |
| `t=a[i]; a[i]=a[j]; a[j]=t` 变成两次写 `a[i]` | 单次使用的值被"就地展开"到使用点，跨过了中间的 `OpUpdate` |
| n-queens 退化成暴力枚举 | 调用的求值被推迟到 phi 拷贝（块尾），越过了 `cols[c] = 0` |
| 循环携带变量每轮多一次存取（n-queens +19%） | 缺少 coalescing，phi 实参与目标被强制分到不同槽位 |

另外修了一个**静默降级**：`code.stackDelta` 把一元运算（`-x`/`not x`）当二元算成 `-1`，
导致任何含负号字面量的函数都算不出上界、退回"指令条数"兜底
（`two_sum` 的 `MaxStack` 从真实峰值 4 变成 112）。这类问题不会算错结果，
但会让静态栈上界形同虚设 —— 现在 `.xlc` 载入校验也依赖它，所以一并修了。
